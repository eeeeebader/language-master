# Status review, 6 Nov 2026

Where the product stands after the Karteikarten, Wörterbuch, Geschichten-Reader, Lektionen and
Admin rounds, what is solid, what is debt, and the order for the next phases: auth, stories,
payments, social, then build, store and field test.

## Review

**Strengths.** The learning loop is coherent: a word met anywhere (lecture, story, dictionary)
lands in the same list model, the same drawer and the same scheduler. Everything is offline-first
with a real sync log design (append-only review events with `supersedes`). Content is data
(Zod-validated lecture and story documents), so the admin console and the audio build read the
same source. The audio story is finished end to end: pack, on-demand, story clips, mute switch.

**Debts worth paying before field tests.**

1. **Dictionary glosses.** Wiktionary sense order is unreliable; v4 fixes ~260 curated words. The
   proper fix is in `build-pack`: rank WikDict translations by `importance`, drop glosses that
   contradict the part of speech, and keep the overrides file under version control. Needs the
   Kaikki and WikDict sources on a build machine (not in the repo).
2. **Admin content drift.** The admin's lecture drafts are the old twelve. Run
   `pnpm --filter @lm/api seed-lectures -- --email <admin> --publish` after deploying so editors
   start from the shipped content.
3. **No pushed history.** 42 commits on `main` exist only on this machine.
4. **Pack size vs. mobile storage.** 21 MB dictionary + 37 MB core audio in IndexedDB. Fine on
   Android; on iOS, Safari may evict IndexedDB after inactivity. Capacitor builds should move packs
   to the filesystem plugin (one afternoon, the `packFiles`/`audioClips` tables are the only touch
   points).
5. **Clock widget**: the hour hand snaps across 12 while dragging; **calendar** starts at today,
   not at the lecture's example date; **path** summaries are cut by character count.
6. **Mock mode in admin** is useful for UI work but drifts from the real API shapes; the users
   page merges three tables client-side because entitlements hang off `auth.users`. A view
   `admin_users` in Postgres would remove that.

## Next phases, in order

### 1. Authentication and sync (1–2 weeks)

Exists: Supabase GoTrue, magic link (`signInWithOtp`), PKCE callback for the native scheme, JWT
check in the API, RLS policies (`rls.sql`), outbox sync scheduler, `/sync` routes.

To do:
- Sign-in screen in Profil with magic link; Google and Apple OAuth once provider keys exist
  (Apple is mandatory for the App Store if any social login is offered).
- Full sync round trip verified on two devices: words, variants, lists, sentences, review events,
  settings, stories. Conflict rule stays "events win, state is derived".
- Account deletion and export from the app (API already has both for admins).
- Consent versioning already blocks the app on a new AGB version; keep it.
- Six-digit user tag: generate on first sign-in (`users.tag`, unique, e.g. `A7K3Q9`, no 0/O/1/I),
  show in Profil, make usernames freely editable. This is the key the social feature searches by.

### 2. Stories (1 week)

Exists: pipeline with writer, annotator, notes, checks, retries and refunds; official texts;
coverage-driven generation request; audio.

To do:
- Generation screen polish: progress state while the pipeline runs (30–60 s), error texts,
  archive limits by tier.
- Official story audio into the core pack is done; ensure `/stories/official` is cached on device
  so the library opens offline.
- Quality loop: a thumbs-up/down on a story plus the LLM usage row gives the admin a cost-quality
  view (analytics page already shows cost per day).

### 3. Payments (1–2 weeks)

Exists: entitlements, token ledger, Stripe checkout and webhook routes, RevenueCat webhook,
pricing in app settings, admin grants.

To do:
- Web: Stripe Checkout for Premium and token packs, Stripe Tax, customer portal link.
- Mobile: RevenueCat SDK in the Capacitor app, products mirrored in App Store Connect and Play
  Console, entitlement sync through the webhook.
- Supporter tip jar web-only, sets `is_supporter` and the badge.
- Test matrix: free limit, token debit and refund on failure, premium archive, restore purchases.

### 4. Social (2 weeks)

Design that fits the existing schema:
- `users.tag` (6 chars) + `profile_visibility` already present.
- Tables: `friendships(user_a, user_b, status: pending|accepted|blocked, requested_by, at)`,
  `shared_items(id, owner, kind: list|story, ref_id, visibility: friends|link)`.
- API: search by tag, send/accept/decline request, friends list with streak, supporter badge,
  current language and this week's minutes (aggregated server-side from synced activity), share a
  list or story, import a shared item into your own library.
- App: Freunde tab inside Profil, friend card, request inbox (reuse the inbox), share sheet on
  list and story menus (the disabled "Teilen" entry is already there).
- Privacy: only aggregated activity, no review history; blocking hides both ways; under-16 is
  already refused at onboarding.

### 5. Build, bundle, test, store (1–2 weeks)

Exists: Capacitor 8 (android project checked in, ios folder), `mobile.yml` workflow, release
workflow building images, Playwright on web.

To do:
- Android: signed release build from CI (keystore in secrets), internal testing track on Play
  Console, Play Integrity not needed yet.
- iOS: Xcode cloud or a Mac runner, TestFlight.
- Store assets: screenshots from the web build at phone size, privacy nutrition labels (data: email,
  usage; no tracking), age rating.
- Device test plan: fresh install → onboarding → core pack download on cellular (prompt?) →
  offline session → sign-in → sync to a second device → story generation → purchase in sandbox.
- Crash and error reporting: Sentry DSN is already wired in the API; add the client SDK.

### 6. Versioned databases

Server: Drizzle schema + numbered SQL migrations under `packages/database/migrations`, applied
on API boot under an advisory lock, recorded in `schema_migrations`. Keep the rule: never edit an
applied migration, add a new file; run `drizzle-kit generate` to diff the schema against the
migration set in CI so the two cannot drift (add that check to `ci.yml`).

Client: Dexie versions 1–4 with upgrade functions. Rule: every schema change is a new
`this.version(n)` with an `upgrade` that transforms rows; add a Vitest that opens a fixture
database at version 1 and upgrades to the current version.

### 7. Deployment for the field test

`docs/infra.md` describes the target: one Hetzner box, Traefik, Supabase compose, API, NLP, Piper,
client and admin as nginx images from GHCR, pull agent via systemd timer.

Checklist:
1. Push `main` to GitHub; CI must be green (it runs lint, typecheck, tests, build).
2. Tag a release so `release.yml` publishes the images; the API image now includes ffmpeg.
3. Server env: `PIPER_URL=http://piper:5000`, `NLP_URL`, `DATABASE_URL` (pooler), JWT secret,
   service role key, CORS origins for `app.<domain>` and `admin.<domain>`, LLM key, Sentry DSN.
4. Run the pull agent once, check `/health`, then `publish-pack.mjs` for dictionary v4 and audio
   core v4 against the server's Supabase, and `seed-lectures` for the admin.
5. Create the first admin user in GoTrue, enable TOTP, give the two or three testers
   `free_stories_per_day` and tokens from the Users page.
6. Point testers at `app.<domain>` (installable PWA) while the store builds are prepared.
